| **UCD-01 — Manage Prescription** | **Owns:** clinical prescription creation, viewing, modification and cancellation; medicine, dosage, quantity, frequency and instructions. **Must NOT own:**pharmacy preparation, stock deduction, physical dispensing, fulfilment status. | **Doctor** | Patient; Pharmacist | • Doctor selects Manage Prescription. • New treatment requires a prescription. • Doctor needs to amend prescription details. • Doctor decides prescription should be clinically cancelled. | **Manage Clinical Prescription** — Doctor retrieves or creates a patient prescription, enters or modifies clinical medication instructions, system validates the data and persists the authorised prescription information. | **S1 Create Prescription S2 Edit Prescription Details S3 View Prescription Details S4 Cancel Prescription** | • Patient not found. • Missing/invalid dosage or medicine information. • Prescription not found. • Modification attempted after dispensing. • Cancellation attempted after dispensing. • Persistence/system error. | **Primary owner of prescription clinical content.** Remove operational statuses such as Preparing/Ready/Dispensed from this use case. Authentication should preferably be a **precondition**, not repeated «include». Original UCD-01 currently combines clinical data and some status behaviour.  |
| **UCD-02 — View Prescription Status** | **Owns:** patient-facing, read-only visibility of prescription and fulfilment progress. **Must NOT own:** editing prescription, changing status, dispensing or modifying inventory. | **Patient** | Doctor; Pharmacist indirectly, because their actions produce the information displayed | • Patient selects View Prescription Status. • Patient receives a notification and opens the prescription. • Patient wants to know medication progress/collection readiness. | **View Prescription and Fulfilment Progress** — System retrieves prescriptions belonging to the authenticated patient and presents relevant prescription information and the latest clinical/fulfilment status without allowing modification. | **S1 View Prescription List S2 View Prescription Details S3 View Current Fulfilment Status** | • No prescriptions found. • Patient account not found. • Prescription no longer exists. • Details cannot be retrieved. • Cancelled prescription. • Already-dispensed prescription. | **Strict query/read use case.** Internally distinguish **Clinical Status** from **Fulfilment Status**, even if the patient UI presents a unified timeline. The original status list combines Pending, Preparing, Ready, Dispensed and Cancelled.  |
| **UCD-03 — Send Alerts and Notifications** | **Owns:** generation, delivery and recording of **patient-facing** notifications triggered by relevant prescription/fulfilment events. **Must NOT own:** deciding prescription validity, changing stock, dispensing, inventory administration. | **System / Event Handler** as operational initiator; **Patient** is recipient | Patient; Pharmacist; Doctor indirectly | • Prescription issued/cancelled. • Medication enters Preparing state. • Medication becomes Ready for Collection. • Medication is Dispensed. • Relevant domain event is published. | **Deliver Patient Notification** — System receives an eligible business event, resolves the patient and notification template, sends the message and records delivery status/history. | **S1 Preparing Medication Notification S2 Ready-for-Collection Notification S3 Dispensed Notification S4 Cancellation Notification** | • Patient information missing. • No qualifying state change. • Delivery failure. • Inactive patient account. • Duplicate notification detected. • Notification provider unavailable. | Better represented as **event-driven behaviour**than direct module-to-module calls. Do not use this use case for every inventory warning. Original UCD-03 already describes automatic notifications resulting from status changes.  |
| **UCD-04 — Authenticate and Authorise User** | **Owns:** authentication, session establishment, identity verification and RBAC permission evaluation. **Must NOT own:** creation of users, assignment/removal of roles, profile editing. | **User** — Administrator / Doctor / Pharmacist / Patient | All system users; Administrator indirectly through access policy | • User attempts login. • Session expires. • User accesses a restricted resource. • Security-sensitive operation requires re-authentication. | **Authenticate Identity and Evaluate Access**— User submits credentials; system validates identity, establishes an authorised session, evaluates assigned RBAC permissions and grants/denies access. | **S1 Login S2 Password Reset / Recovery S3 Authorisation Check S4 Session Establishment** | • Invalid credentials. • Account disabled/locked. • Insufficient permission. • Expired session. • Password reset token invalid/expired. • Authentication service unavailable. | Rename from **“Login & Role Management”** to simply **Authenticate and Authorise User**. Role administration belongs to UCD-06. Original UCD-04 combines login with RBAC permission checking.  |
| **UCD-05 — Manage Profile** | **Owns:** self-service modification of permitted personal/profile information and personal security preferences. **Must NOT own:** role assignment, account activation/deactivation, administrative account lifecycle. | **Authenticated User** | Administrator, Doctor, Pharmacist, Patient — each acts on **their own** profile | • User opens My Profile. • Contact/address information changes. • User wants to change password. • User updates personal preferences. | **Maintain Own Profile** — Authenticated user views current personal information, changes permitted fields, system validates the changes and updates the user's profile. | **S1 View Profile S2 Edit Personal Information S3 Change Password S4 Update Contact / Preference Information** | • Invalid field format. • Weak/invalid password. • Incorrect current password. • Restricted field modification attempted. • Concurrent profile update. • Save failure. | Separate **Profile** from **UserAccount**. Self-service attributes belong here; RBAC/account lifecycle belongs to UCD-06. Current source allows all users to edit their own profile and security information.  |
| **UCD-06 — Manage User Accounts** | **Owns:** administrative account lifecycle: create, activate, disable, unlock and administer role assignments/access status. **Must NOT own:** normal self-service profile editing or authentication execution. | **Administrator** | Patient; Doctor; Pharmacist; other Administrators | • New user onboarding request. • Registration requires approval. • Role/access changes requested. • Account needs disabling/reactivation. • Security administrator needs to unlock an account. | **Administer User Account Lifecycle**— Administrator locates or creates an account, configures identity/access attributes and role assignments, validates constraints, then persists the authorised account change. | **S1 Create User Account S2 Approve Registration S3 Assign / Remove Role S4 Enable / Disable Account S5 Unlock Account** | • Duplicate username/email. • Required fields missing. • Invalid/non-existent role. • Attempt to remove required administrative access. • Account not found. • Concurrent administrative modification. | **Administrative command use case.** UCD-04 evaluates roles; UCD-06 administers them. Standardise source ID UC06→ **UCD-06**. Original draft explicitly assigns account creation and role assignment to Admin.  |
| **UCD-07 — Update Prescription Status** | **Owns:** **clinical prescription lifecycle transition only**. Recommended states: Draft/Issued/On Hold/Cancelled/Expired or equivalent clinical states. **Must NOT own:** editing dosage/medicine details, Preparing/Ready/Dispensed states, stock or physical dispensing. | **Doctor** | Patient; Pharmacist | • Doctor clinically approves/issues prescription. • Patient condition requires prescription hold/cancellation. • Prescription validity expires. • Doctor reviews treatment status. | **Update Clinical Prescription Lifecycle** — Doctor selects an existing prescription and requests an authorised clinical status transition; system validates the transition rules and updates only the clinical lifecycle state. | **S1 Issue Prescription S2 Place Prescription On Hold S3 Cancel Prescription S4 Resume / Reactivate Where Permitted** | • Prescription not found. • Invalid state transition. • Prescription already fulfilled where transition is forbidden. • Actor lacks permission. • Concurrent status modification. • Update persistence failure. | **Major refactor from current draft.** Delete UCD-07 Edit Details; that duplicates UCD-01. Remove «extend» → Dispense Medication; dispensing should follow workflow/state/event progression rather than UML extension. Current UCD-07 substantially overlaps Manage Prescription.  |
| **UCD-08 — Dispense Medication** | **Owns:** pharmacist-controlled fulfilment transaction: verify prescription/patient, confirm medication quantities, execute dispensing, request inventory deduction and complete fulfilment. **Must NOT own:** general medicine master-data administration, prescription authoring or notification delivery implementation. | **Pharmacist** | Patient; Doctor indirectly; Inventory domain; Notification subsystem | • Pharmacist selects an eligible prescription for fulfilment. • Patient arrives for collection. • Medication has reached Ready-for-Collection state. | **Complete Medication Dispensing Transaction** — Pharmacist selects an eligible prescription, system verifies patient/prescription and stock availability, pharmacist confirms handover, system records dispensing, deducts stock and publishes the resulting fulfilment event. | **S1 Verify Prescription and Patient S2 Check Stock Availability S3 Confirm Dispensing S4 Deduct Inventory S5 Complete Fulfilment** | • Insufficient/out-of-stock medicine. • Patient verification mismatch. • Prescription cancelled/expired/not eligible. • Quantity mismatch. • Concurrent stock change. • Inventory deduction failure. • Transaction persistence failure. | Treat this as an **application orchestration use case**, not one God Service. Manage Medicine Inventory may provide inventory capability, but UCD-08 should not administratively manage inventory. Original UCD-08 currently combines dispensing, stock update and notifications.  |
| **UCD-09 — Generate Reports** | **Owns:** authorised, read-only reporting/aggregation across operational data. **Must NOT own:**operational mutation, stock adjustments, prescription modification or account changes. | **Administrator** | Pharmacy management; Pharmacist/Doctor only as data-origin stakeholders, not report actors unless requirements later change | • Administrator opens reporting dashboard. • Periodic management review. • Audit/compliance request. • Administrator needs prescription/dispensing/inventory summary. | **Generate Operational / Management Report** — Administrator selects report type and criteria; system retrieves authorised read-model data, aggregates results and displays or exports the report. | **S1 Prescription Report S2 Dispensing Report S3 Inventory Report S4 User / Access Report**if required **S5 Export Report** | • Invalid date/filter range. • No matching records. • Insufficient reporting permission. • Reporting data unavailable. • Export generation failure. • Query timeout. | **Read-only downstream module.** Remove Pharmacist association from the UML unless Pharmacist reporting is explicitly required. Source UCD-09 only specifies Admin and otherwise leaves the section largely blank.  |
| **UCD-10 — Manage Medicine Inventory** | **Owns:** medicine master records, stock receipt, batch/expiry information, authorised stock adjustments, stock-level visibility and threshold monitoring. **Must NOT own:**prescription authoring, patient-facing notifications or complete dispensing transaction. | **Pharmacist** | Patient indirectly; Administrator/management; Dispensing process | • New stock received. • Pharmacist needs inventory correction. • New medicine added. • Stock/batch/expiry information changes. • Pharmacist checks low-stock condition. | **Maintain Medicine Inventory** — Pharmacist searches or selects a medicine, performs an authorised inventory operation, system validates quantities/master data, commits the stock transaction and updates available inventory. | **S1 Add Medicine S2 Update Medicine Information S3 Receive Stock S4 Adjust Stock S5 View Inventory / Batch Details** | • Duplicate medicine. • Invalid quantity. • Negative stock attempted. • Low-stock threshold reached. • Expired batch detected. • Concurrent stock update. • Database/transaction failure. | **Authoritative inventory module.** Dispensing calls its inventory capability but does not own inventory administration. Low-stock warning is operational; do not automatically treat it as a patient notification. Source UCD-10 identifies Pharmacist but leaves most details unfinished.  |
